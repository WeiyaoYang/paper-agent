# 个人论文学习与讨论 Agent：架构、实现与面试说明

整理日期：2026-10-23。本文面向需要理解整个项目的读者，也可作为后续交给 GPT 的项目上下文。内容依据当前 README、设计文档与源码，区分实际实现、设计动机和未来方向。本文不是性能评测报告，也不把离线测试等同于真实模型效果。

## 1. 项目定位与解决的问题

这是一个面向个人的论文学习与讨论 Agent。用户指定一篇论文和理解目标，系统结合用户画像、知识框架和实际对话，自主制定规划、选择学习行为、验证理解，并保存带来源和关联关系的成果。

目标用户以中文为母语，计算机与 AI 基础不均衡，希望先完成项目，再补齐过程中需要的知识。直接阅读英文论文会遇到术语、前置知识和方法理解的多重困难；普通论文总结又无法判断用户到底理解到什么程度。

因此，项目关注的不是一次性生成摘要，而是把“读到了什么”推进到“能否回答与目标有关的问题”，并留下下一次可以使用的材料和学习经历。项目最初提出的两个业务场景是：

1. 新论文学习：判断范围、安排学习、讲解与提问，最后验证理解。
2. 观点讨论与历史材料利用：围绕论文讨论依据和限制，利用已有知识记录。

当前版本重点打通第一种场景，同时支持指定论文下的探讨行为。跨论文历史语义检索、脱离指定论文的自由研究并未实现，不能把第二种场景的完整愿景描述成现成功能。

## 2. 用户实际如何使用

在项目目录的 PowerShell 运行：

```powershell
cd '你的项目目录'
.\scripts\run.ps1 chat
```

只有一篇论文时自动选择，随后输入目标。也可提供本地 PDF 或已登记编号：

```powershell
.\scripts\run.ps1 chat 'D:\papers\example.pdf' --goal '理解方法的输入输出和核心直觉，不要求公式推导'
```

全部交互在同一个终端进行。回答可多行，单独一行 `.` 提交；候选记录出现后输入 `保存` 才写入正式成果。`:do reading ...` 等命令可主动指定行为；`:end` 请求进入理解验证；`:pause` 暂停；`:stop` 明确提前结束。通过验证与结果复盘后，用户输入 `结束` 才正常完成。暂停后使用 `chat --resume CHAT_ID` 恢复。

本地 PDF 先归档、去重并检查可用性，缺少内容时解析；有可用版本则复用。模型接收必要论文材料、画像和框架，通过 OpenAI 官方 API 调用，产生独立 API 费用。

## 3. 为什么它是 Agent，而不只是固定工作流

项目同时包含确定的流程约束和模型驱动的自主决策。

确定的约束包括：材料必须可用、正式记录必须校验、正常结束前必须验证、核心画像不可在学习中修改。自主决策包括：目标是否需要澄清、需要补读哪些页、选择阅读还是探讨、如何提问，以及失败后补什么。

代码没有写死“阅读一次 → 问答一次 → 笔记一次”的顺序。调度模型根据当前目标、计划、真实记录与用户反馈输出下一行为和理由；执行过程中，模型继续选择工具，获取结果后再决策。未通过验证时，依据实际缺口生成新版规划，而不是固定重复相同步骤。

更准确的定位是：**具有明确边界和持久化状态的单 Agent 学习系统，采用规划、行为选择、工具执行和反馈重规划的循环。** 它有工作流作为运行边界，但边界内的路径由模型决定。不是多 Agent 系统，没有自由执行任意代码的能力，也不是用户每一步手工选择的菜单程序。

## 4. 总体架构与模块协作

```text
终端用户
   │ 目标、真实回答、保存/结束/暂停
   ▼
交互层 app/chat.py + 命令入口 app/cli.py
   ▼
统一协调层 LearningSession（agent/session.py）
   ├─ Planner：初始规划、按反馈重规划
   ├─ 调度模型：选择下一行为、执行要求与理由
   ├─ BehaviorRunner：加载行为说明，执行工具交互循环
   └─ LearningReviewer：汇总实际结果、生成 reason、衔接新规划
            │
            ├─ 模型适配层 models/client.py → OpenAI Responses API
            ├─ 材料工具 ingestion/ → PDF 归档、解析、读取与检查
            ├─ 记忆输入 memory/profile.py + 正式记录与知识框架
            └─ 存储校验 storage/ + schemas/ → 引用、结构、写入
                          ▼
              data/results、runs、artifacts、logs
```

这里的“中间模块”主要是协调层和执行层：它们把模型建议转换为允许执行的动作，把工具返回和用户反馈转换为下一轮上下文，并维护暂停、提交和完成条件。模型不会自行扫描目录来理解项目；程序明确加载指令、上下文、工具定义和输出结构。

采用 Python 自建协调循环，使用 OpenAI SDK、JSON Schema、Docling 和 pdfplumber；没有使用 LangChain、LangGraph 或向量数据库。类名中有多个职责模块，不意味着运行多个独立 Agent。

## 5. 规划模块如何实现

核心代码为 `src/paper_agent/agent/planning.py` 中的 `Planner`。

程序先检查论文与当前解析版本，然后组装：用户原始要求、材料元信息、首页文本、章节标题、解析限制、个人画像、知识框架和行为简介。全文不会默认一次发送给模型；模型可以调用 `read_paper_pages` 补读，每次最多三页。

程序把总指令、材料准备说明和规划说明拼接为本轮 `instructions`，同时提供三个工具：

| 工具 | 作用 |
|---|---|
| `read_paper_pages` | 在指定论文范围内补读页面与内容块 |
| `ask_user` | 澄清目标中的重要歧义，并暂停等待真实回复 |
| `submit_plan` | 提交结构化规划，不代表已经执行计划 |

规划保存 `part=planning`、`goal`、论文与内容版本配对引用、行为与说明组成的 `plan`。程序检查材料编号、当前解析版本、可选行为以及是否包含必经 `verification`。

规划是一份可调整的行动建议，不是只能逐项执行的脚本。后续调度仍根据实际进展重新选择行为。失败后的新版规划保留原目标，并利用真实验证缺口调整重点。

当前规划格式较简洁，没有独立建模复杂任务依赖图、时间估算或计划搜索算法。所谓“规划能力”由大模型结合上下文和工具实现，不是项目训练了一个规划模型。

## 6. 自主调度与行为模块

### 6.1 调度模型负责选择能力

`LearningSession.select()` 提供当前规划、已保存记录摘要、最近真实输入、部分暂停对话和行为简介。模型通过结构化输出返回：

```json
{
  "behavior": "reading",
  "request": "围绕本次目标解释论文的输入与输出",
  "reason": "需要先建立方法的整体理解，再进行验证"
}
```

这是格式示例，不是已发生的执行记录。代码校验行为属于允许集合，再启动执行器。用户明确指定行为时由程序处理覆盖；用户请求结束时由程序确保先进入验证。

### 6.2 行为是项目内的轻量 Skill

`behaviors/*.md` 描述用途、输入、工具与产物；选定行为后加载其完整说明。公共代码留在 `src`，不为每一种行为重复实现模型循环、PDF 读取和保存逻辑。

| 行为 | 用途 | 正式产物 |
|---|---|---|
| reading | 读取和解释材料 | 阅读记录 |
| discussion | 分析观点、依据、分歧与限制 | 探讨记录 |
| qa | 解释、提问、反馈与追问 | 问答记录 |
| knowledge-recording | 提炼可复用知识 | 知识点与关联知识笔记 |
| verification | 验证本次目标是否达成 | 专用验证问答记录 |
| framework-change | 核心框架修改 | 当前禁用 |
| profile-change | 长期画像修改 | 当前禁用 |

材料准备和学习规划也有辅助说明文件，但不作为额外可选学习行为。Markdown 文件本身不会执行，也不是已经安装到平台的标准 Skill；生效依赖程序加载、工具权限和执行逻辑。

### 6.3 执行器负责模型与工具的循环

`BehaviorRunner` 复用 `Planner` 的有界工具循环，加载当前行为指令，提供适用工具。模型可读取论文、向用户解释或提问、查询知识点、读取允许的本次学习记录，最后提交候选。

`talk_to_user` 会真正暂停等待用户，`propose_record` 只产生候选。正式保存由用户本地命令触发，模型不能仅凭一句“保存成功”改变数据。

## 7. 工具调用如何实现

工具定义包含 `name`、`description`、`parameters` 和 `strict`。描述帮助模型判断何时调用；参数 Schema 限定输入；Python 分发代码负责实际执行。

一次典型循环是：

```text
发送指令、上下文、工具定义
  → 模型返回 function_call
  → 程序解析名称与参数，执行本地校验
  → 调用允许的实现
  → 按 call_id 返回 function_call_output
  → 模型继续读取、提问或提交
```

工具调用不是模型直接运行函数，也不是模型获得任意文件访问权限。规划和行为阶段提供不同工具；验证专用工具不开放给普通阅读。当前工具调用禁止并行，循环期望每次恰好一个函数调用，以简化状态转换和真实交互。

关键工具还包括：

| 工具 | 工程边界 |
|---|---|
| `find_knowledge_points` | 查询既有知识点名称和别名，不是向量检索 |
| `read_learning_record` | 仅按本次上下文提供的记录编号读取，不接收任意路径 |
| `ask_verification_questions` | 程序分配题号，保存实际问题并等待真实回答 |
| `propose_record` | 校验候选后展示，不能直接写正式成果 |

普通参数或引用错误会以工具错误反馈给模型，允许其在调用上限内修正。API 请求失败或不确定中断不会自动重放；这与“模型在下一轮修正参数”是两种不同情况。

## 8. 记忆、知识存储与 RAG 的关系

### 8.1 当前记忆不是单个数据库

本项目把“系统记得什么”和“数据放在哪里”分开理解。画像、框架、历史经历和知识内容都存为本地文件，由不同模块加载；`memory/profile.py` 主要负责读取并校验画像，不是一个可以自动操作所有数据的记忆中枢。

| 记忆角度 | 当前载体 | 使用方式 |
|---|---|---|
| 长期个人信息 | `results/1profile/current.json` | 规划与行为开始时加载，只读 |
| 知识组织参照 | `results/2knowledgeframework/knowledge.txt` | 当前作为完整文本加载，只读 |
| 本次工作记忆 | 子任务 history、真实 messages、会话输入与状态 | 延续工具调用和当前交互 |
| 学习经历 | 规划、结果、阅读/问答/探讨记录 | 调度读取摘要，必要时受限读取完整记录 |
| 可复用知识 | 知识点和知识笔记 | 名称/别名查询、关联保存，尚无全库语义召回 |

### 8.2 为什么画像与知识内容分开

“论文说了什么”与“用户掌握了什么”需要不同证据。模型解释或单次回答不应自动成为长期能力结论。因此当前学习流程只读画像和框架，知识笔记也保留未验证状态。一次验证通过只说明本次目标范围内的表现。

### 8.3 当前没有实现 RAG

RAG 是检索外部资料并加入生成上下文的方法，不等同于数据库或记忆。当前已有资料读取和精确查询，但没有 embedding、向量索引、语义召回、重排序及跨论文检索评估，不能宣称“搭建了完整 RAG”。

未来可以在正式材料和笔记之上增加派生索引，检索后保留论文、解析版本、页码和知识笔记编号。原始正式记录仍应作为事实来源，索引可重建；画像不必因此全部向量化。这个方向尚未开发。

## 9. 上下文与 Prompt 如何组织

| 层级 | 文件或数据 | 作用 |
|---|---|---|
| 总规则 | `prompts/agent-policy.md` | 目标、边界、真实回答、验证和保存原则 |
| 当前阶段/行为 | `behaviors/*.md`、dispatch、learning-review | 限定本轮职责与输出 |
| 工具定义 | Python 中的 description 与参数 Schema | 告知模型可以执行什么 |
| 参考上下文 | 用户要求、论文、画像、框架、真实记录 | 支撑本次判断 |
| 历史与反馈 | 工具输出、真实用户回答、前轮缺口 | 推动后续行动 |

程序显式把总规则送入 API 的 `instructions`，每次调用继续提供；不是模型看见项目目录就自动读取它。选行为时先给简介，执行时再给完整行为说明，属于按阶段装配上下文。

当前还采用局部控制：首页与章节先提供、每次补读最多三页、调度只带有限数量的记录摘要和输入、完整记录按编号读取并限制单次返回大小。这降低无关上下文，但不是完整的 token 预算器。框架仍整份注入，长会话工具历史仍可能膨胀，是后续优化点。

论文和历史材料被声明为参考数据，不能因其中出现指令就改变工具权限。程序的工具白名单、路径限制和写入校验提供额外边界；这些措施不能被描述成已经彻底解决 Prompt Injection。

## 10. 十类结构化信息与存储设计

| 类别 | 主要内容 | 更新机制 |
|---|---|---|
| 1 个人画像 | 背景、偏好、方向、知识掌握信息 | 学习中只读 |
| 2 知识框架 | 分类体系与知识组织参照 | 学习中只读，当前文本形式 |
| 3 学习笔记 | planning 与 result，连接本次目标和产物 | 规划提交、验证后复盘 |
| 4 论文 | 稳定编号、标题、来源、PDF 路径、哈希与解析状态 | 导入/解析工具成功后程序更新 |
| 5 论文内容 | 解析版本、页文本、块、页码、坐标、限制 | 程序保存解析版本 |
| 6 阅读记录 | 范围、重点、总结、疑问、真实对话 | 行为候选经用户保存 |
| 7 问答记录 | 问题、回答、反馈；含验证专用记录 | 行为候选经用户保存 |
| 8 探讨记录 | 观点、依据、分歧、阶段结论 | 行为候选经用户保存 |
| 9 知识笔记 | 知识内容、来源、关联、验证状态 | 知识记录行为保存 |
| 10 知识点 | 名称、别名、分类、关系 | 知识记录行为创建或精确复用 |

从信息用途看，还有另一个互不冲突的分类：知识与个人资料、任务状态与经历、临时工作信息。过程状态也需持久化，不能简单说“状态不保存、数据才保存”。

目录按用途分离：

```text
data/
  papers/       原始 PDF
  results/      十类正式信息
  artifacts/    Docling 原始结果、导出等可追溯副产物
  runs/         会话、工具历史、候选、版本关系与失败现场
  logs/         模型调用耗时、用量及错误元信息
```

模型候选和运行快照不会自动成为正式知识。正式记录用 UUID 标识，不是目前按日期或自增整数编号。论文稳定 ID 与解析版本 ID 分离，避免重新解析后旧引文失去语境。

JSON Schema 负责结构校验，但不替代业务校验：程序还核对材料归属、版本、已读页、引文、目标和状态。画像目前由专门代码校验，知识框架还没有节点 Schema；并非十类都有一一对应的独立 Schema 文件。

## 11. PDF 工具与证据链

材料层负责 PDF 哈希去重、归档、登记、解析和可用性检查。Docling 提供结构化提取，pdfplumber 提供另一种解析后端。保存逐页文本与内容块，保留原始解析产物、版本和限制。

引用可以指向论文 ID、内容版本、页码、可选块与 quote。程序检查引用来自本次已经提供或读取的页面，核对归属及引文实际存在；坐标按解析器记录的坐标原点解释。

这形成“学习结果 → 正式记录 → 引文 → 具体解析版本 → PDF”的追溯链。它证明的是引用位置与文本可核对，不能证明模型推论正确、引用足以支持结论或用户已经理解。

Docling 内部可能使用模型，但在本系统里属于程序调用的解析工具，不是负责规划和讲解的对话模型。当前公式、图片语义、扫描件和复杂表格仍有限制。

## 12. 验证、复盘与反馈重规划

验证是独立行为，不用普通聊天或模型自称“用户理解了”代替。

1. 模型根据本次目标提出若干问题，不固定五题。
2. 程序分配题号，展示并等待真实回复，不提前给出参考答案。
3. 保存用户原始回复；整组一起回答时，各题保留同次原始文本，不由模型伪造拆分后的原话。
4. 模型逐题给出 correct、partial、incorrect 或 insufficient_evidence，以及参考答案和反馈。
5. 程序拒绝没有真实回答、漏评或部分正确却声称总体通过的候选。
6. 用户确认保存后，复盘模块生成 result，再决定新版规划或结束确认。

`LearningReviewer` 中，模型负责 reason 和问题依据的提炼；代码从正式验证读取是否达标，并汇总真实关联产物。变化清单只包含实际使用、创建的材料或记录，不编造修改。

失败后保留旧结果，以共同 `study_id`、递增 `revision`、`previous_plan_id` 连接新版规划。当前这些版本关系主要放在运行状态中，正式 planning JSON 本身较简洁。正常结束要求当前验证通过、对应 result 已保存以及用户明确确认。

这是一种基于任务反馈的重规划，可以类比反思循环，但不是模型参数训练、强化学习或已经验证有效的自动教学算法。评分质量仍依赖模型，需要进一步评估。

## 13. 流程控制、可靠性与监控

流程控制器负责“现在允许做什么”，监控负责“实际发生了什么”。二者分离。

`LearningSession` 保存 planning、selecting、behavior、reviewing、decision、ended 等阶段，以及等待回答、等待保存、暂停、阻塞和完成等状态。子任务另有运行状态。等待用户时暂停模型循环，恢复时使用已保存状态继续。

主要工程措施：

- **有界执行**：统一会话默认最多 40 次 API 尝试，跨版本累计；单个规划或行为最多 8 次。次数不是美元预算。
- **不盲目重放**：调用前保存 in_flight 等标志；失败或中断后遇到不确定现场停止，避免重复计费或提交。代价是目前需要人工检查，不具备自动故障修复。
- **显式提交**：候选和正式成果分开，用户本地确认后写入；规划和结果复盘按系统规则自动衔接保存，并非所有文件都要求逐一确认。
- **版本检查**：核对论文解析版本；验证记录关联规划内容哈希，避免针对变更后的计划错误宣称通过。
- **文件写入保护**：单文件先写临时文件再替换；普通批量写入失败回滚新文件。没有断电级多文件事务保证。
- **统一入口锁**：chat 用操作系统文件锁防止多个统一会话同时写入。单项开发命令不具有完整全局并发保护。
- **现场与日志**：保存运行状态、模型响应、候选和调用元信息。用量日志不记录密钥或完整请求正文，但运行快照会包含材料、画像和对话，仍是私人数据。

API 层固定官方地址、`store=False`、禁用 SDK 自动重试，规范化错误并记录用量。无服务器会话存储不代表本地无数据：程序保留历史输出与所需 reasoning continuation 信息，用于后续调用和恢复。

| `prompts/` | 总规则、行为调度与学习复盘指令 |

| `agent/behavior.py` | 行为指令加载、交互、候选、提交和验证 |
| `agent/review.py` | 结果、真实变化清单和失败重规划 |

## 15. 验证证据与当前边界

截至已有 2026-10-22 检查报告，48 项离线测试通过，覆盖完整的“规划 → 阅读 → 验证失败 → 新规划 → 问答补缺 → 再验证通过 → 结束”，以及暂停恢复、行为覆盖、预算、进程锁、引用、Schema 和写入失败。测试以模拟模型和临时数据进行，不等于模型学习效果评测。

早期规划及阅读、探讨、问答、知识记录四类行为曾经过真实 API 验证。新的理解验证、结果复盘和统一调度组合此前只完成离线验证；本文没有新增真实 API 调用，也不宣称完整真实端到端已经通过。用户启动试用不等于已经得到成功证据。

当前已有 π₀ 论文材料，可用于运行验证。系统主要面向单用户、单篇指定论文、本地使用；没有多租户服务、Web UI、跨论文研究、RAG 索引、自动画像更新、知识图谱、语义去重或全局金额预算。保存新知识时主要按规范化名称与唯一别名复用，尚无既有正式知识的通用修改接口。

当前最重要的缺口是实际使用与效果评估，而不只是增加工具数量。还需确认真实模型在行为选择、来源使用、验证难度和重规划上是否稳定，建立可重复评估案例，再优化上下文成本、恢复机制和历史检索。

## 16. 面试中值得讲清楚的设计取舍

| 取舍 | 选择与理由 | 代价 |
|---|---|---|
| 自主规划与确定性 | 模型选择路径，代码执行不变约束 | 需精细设计状态和权限 |
| 直接写入与候选提交 | 行为成果先审阅再正式保存 | 交互步骤增加 |
| 自由记忆更新与核心只读 | 画像、框架暂时只读，避免一次判断污染长期信息 | 个性化尚不会自动演进 |
| 数据库与文件 | 小规模单用户先用 JSON/Markdown，方便检查与追溯 | 查询、事务和并发能力有限 |
| 全文注入与按需读取 | 首页和标题起步，工具补读，摘要加受限完整记录读取 | 可能漏读，需要评估补读决策 |
| 失败自动重试与费用确定性 | 不自动重放不确定调用 | 需要人工恢复 |
| 框架与自建循环 | 自建小型协调器，明确学习 Agent 基础机制 | 自行承担恢复和演进工作 |
| 完全自由工具与受限工具 | 按阶段提供白名单工具和严格参数 | 泛化范围受限，但当前任务更可控 |

这些选择围绕真实规模做取舍，不意味着数据库、Agent 框架或自动重试本身不好。未来规模变大时，应根据事务、检索和维护成本重新选择。

## 17. 面试讲述示例

### 一分钟版本

我围绕自己的英文论文阅读需求做了一个个人论文学习 Agent。它不是只生成摘要，而是根据论文、用户画像和学习目标生成规划，再自主选择阅读、讨论、问答或知识记录，最后通过真实回答验证是否达到目标；失败则保留旧结果并重新规划。

实现上我使用 Python、自建协调循环和 OpenAI 工具调用。模型负责选择行动和内容判断，程序负责工具权限、状态、结构与引文校验、调用上限和文件保存。行为说明类似轻量 Skill，公共工具和执行代码复用。项目已经有统一终端和离线闭环测试，部分能力经过真实 API 验证；当前还没有向量 RAG，也没有自动修改长期画像。

### 深入介绍时的顺序

1. 先讲用户为什么需要个性化学习和验证，定义成功条件。
2. 展示自主选择行为的循环，说明哪些由模型决定、哪些由代码保证。
3. 用一次补读或真实提问说明 function calling、等待与恢复。
4. 展示一条记录如何关联规划、论文版本和引文，说明候选与正式数据分离。
5. 展示一次失败验证如何推动新版规划，强调保留原目标与真实反馈。
6. 最后说明测试证据、未实现能力、当前限制及下一步评估。

以上是技术叙述样例。项目由用户与 AI 编程助手协作开发，个人职责应按实际参与情况说明，例如需求定义、架构讨论、代码审查、测试和迭代。不能据本文声称独立手写了所有代码、线上服务了大量用户或取得未测量的效果提升。

## 18. 常见追问与回答要点

**Agent 和 workflow 的区别在哪里？** 有确定的运行边界，但不固定学习路径。模型选择补读、澄清和下一行为，根据结果调整；控制器保证验证、权限和结束条件。

**规划是否只是生成一段文本？** 输出是经过 Schema 和业务规则校验的计划；执行由独立调度根据真实进度选择，失败还有版本化重规划。但尚无计划搜索和依赖图算法。

**怎么保证工具调用正确？** 描述帮助选择，严格参数帮助格式，程序白名单和业务校验约束执行。工具结果回传后模型再判断；不能保证语义决策总正确。

**记忆怎么做，为什么不用 RAG？** 画像、框架、工作历史和正式知识分层存储，目前按阶段加载、摘要和精确查询。小规模先打通证据链；跨论文语义检索是后续需求，尚未实现。

**怎么避免幻觉进入知识库？** 保存真实对话、版本化引文校验、候选审阅、知识未验证标记、核心画像只读。它们降低污染风险，不等于消除幻觉。

**怎么判断用户理解？** 根据目标提问，等待真实回答，模型逐题评估，代码保证完整性和一致性。正确性仍需人工审查和评估集；不把单次通过推断成长久掌握。

**怎么处理中断和成本？** 持久化状态，调用次数上限跨版本累计，不自动重放可能计费的请求。当前没有精确金额硬限或自动恢复，需继续完善。

**效果如何证明？** 工程行为有离线测试，部分工具链有真实 API 验证；教学效果、调度质量和成本收益尚无系统量化数据。下一步可统计目标达成率、评分与人工一致性、工具错误率、每次学习 token 与费用、无效重复行为次数。

这些指标是建议的未来评估方案，当前没有相应结果或提升百分比。
